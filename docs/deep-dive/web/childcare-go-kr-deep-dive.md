# 임신육아종합포털 아이사랑 Deep Dive — 구조·기능·문제 해결 방식

> 조사 기준일: 2026-11-08  
> 공식: https://www.childcare.go.kr/

## 1. 서비스 한 문장

아이사랑은 **월령별 육아정보와 어린이집·보육료·가정통신문·상담 등 국가 보육서비스를 한 포털/앱에 묶은 공공 육아 인프라**다.

## 2. 두 개의 서로 다른 제품이 결합되어 있음

### A. Parenting Knowledge
- 성장발달
- 관계와 소통
- 행동
- 안전
- 수유/영양
- 배설
- 수면
- 건강과 일상
- 놀이와 학습

### B. Childcare Administration
- 어린이집 검색
- 보육료 결제
- 카드/지원내역
- 가정통신문
- 상담

즉:
```
육아 지식 포털
+
보육 행정 서비스
```
의 결합체다.

## 3. 월령별 정보구조

1~3개월 페이지에서 확인되는 상위 항목:
- 성장발달
- 관계와 소통
- 행동
- 안전
- 수유
- 배설
- 수면
- 건강과 일상
- 놀이와 학습

13~24개월 등 이후 시기에도 유사한 영역을 유지하면서 내용이 바뀐다.

이것은 **stable taxonomy + age-varying content** 구조다.

장점:
- 부모가 메뉴 구조를 다시 학습할 필요 없음
- 같은 항목을 시기별로 비교 가능

## 4. 국가 정보의 메타데이터

성장 정보는 질병관리청 성장도표 등 공식 자료원을 표시한다.

이런 provenance 표시는 민간 앱도 배워야 한다.

```
Content
├─ source
├─ reference year
└─ authority
```

## 5. 정보 콘텐츠의 특징

아이사랑의 목적은 "오늘 몇 시에 재울까" 같은 개인화 예측이 아니다.

대신:
- 해당 월령에서 무엇을 알아야 하는가
- 어떤 위험을 조심해야 하는가
- 어떤 놀이/생활이 적절한가

를 넓게 커버한다.

따라서 **coverage reference**로 매우 좋다.

민간 앱을 설계할 때 빠진 영역을 점검하는 체크리스트로 사용할 수 있다.

## 6. 어린이집 검색의 구조

모바일 서비스 안내 기준:
- 위치 기반 검색
- 시설 유형/특성
- 평가정보
- 현원/정원
- 통학차량
- 좋은어린이집 필터

즉 일반 지도검색이 아니라 **부모의 의사결정 속성**을 구조화한다.

```
Location
+
Facility attributes
+
Capacity
+
Evaluation
→ shortlist
```

## 7. 보육료 결제/지원

육아 앱들이 주로 기록·정보를 다루는 반면 아이사랑은 실제 행정 transaction을 수행한다.

- 보육료 결제
- 카드 발급 내역
- 결제현황
- 연간 지원내역

이는 **information → action → official transaction**까지 연결된 공공서비스다.

## 8. 가정통신문

어린이집에서 보낸 가정통신문을 모바일 알림으로 연결한다.

아기가 성장해 기관에 들어가면 사용자 핵심 과업이:
```
가정 돌봄
→ 기관과의 정보교환
```
으로 전환됨을 보여준다.

## 9. 강점

- 국내 공식 정보
- 월령별 광범위한 coverage
- 보육 행정과 실제 transaction
- 어린이집 탐색
- 기관 커뮤니케이션

## 10. 구조적 한계

### IA 규모
공공 포털 특성상 기능과 메뉴가 매우 많다.

### 개인화 깊이
기록 데이터 기반 추천은 제한적이다.

### 읽기→실천 연결
콘텐츠가 많지만 오늘 할 일로 자동 변환되는 정도는 약하다.

### 앱/웹 일관성
행정 기능과 육아 콘텐츠가 서로 다른 제품처럼 느껴질 수 있다.

## 11. 민간 앱에 가져올 것

1. **Stable age taxonomy**
2. **공식 source provenance**
3. **육아 전 영역 coverage**
4. **Childcare transition**
5. **Search attributes for institutions**
6. **정보와 행정행동을 연결**
